### 1. Τι κάνει αυτό το εργαλείο (Plain Greek)

Το RoomRate API μετατρέπει τα δεδομένα τιμών από τη βάση PostgreSQL σε καθαρά endpoints για dashboard, χάρτη ανταγωνιστών και μελλοντικούς AI agents. Ο ξενοδόχος πρώτα κάνει login, δηλώνει το δικό του κατάλυμα και περιοχή, διαλέγει το σωστό Booking property και μετά η εφαρμογή κάνει αυτόματο live scrape για να βρει τους τύπους δωματίων του. Στον χάρτη ο χρήστης διαλέγει room type και filters, πατά `Find Competitors`, ξεκινά νέο live scrape ανταγωνιστών και βλέπει μόνο τα συγκρίσιμα δωμάτια που επέστρεψε αυτό το job.

### 4. How to Run

**FastAPI server:**
```bash
uvicorn api.main:app --reload --port 8000
```

**Swagger docs:**
```text
http://localhost:8000/docs
```

**Health check:**
```bash
curl http://localhost:8000/health
curl http://localhost:8000/ready
```

**Production Python worker (separate service/process):**
```bash
# Environment: ROOMRATE_PROCESS_ROLE=worker
python -m api.worker
```

In production the FastAPI service uses `ROOMRATE_PROCESS_ROLE=api`; it only
persists jobs. The worker uses `ROOMRATE_PROCESS_ROLE=worker`; it claims and
executes them. `ROOMRATE_PROCESS_ROLE=all` is reserved for local development.

**Angular frontend app preview:**
```bash
cd frontend
npm install
npm run dev
```

Open:
```text
http://127.0.0.1:4200
```

The Angular app is gated by Supabase Auth. Signed-out users go to `/auth`. The sign-up form collects email/password plus accommodation name and location as onboarding draft values, then shows a clear email-confirmation message when Supabase requires confirmation. The sign-in screen also has a resend-confirmation action for users who did not receive the first email, while still surfacing Supabase rate-limit errors clearly. Sign-in uses Supabase's password grant through a timeout-controlled browser request, then stores the returned session in the Supabase client. The password field has a property-bound show/hide toggle so test users can reveal the typed password before pressing sign-in. The auth page shows the active step (`Signing in`, `Checking workspace`, `Finding your property`, `Discovering rooms`, `Opening map`) so live Booking work is not mistaken for a frozen login. FastAPI browser calls also have explicit client-side timeouts, so an unreachable backend or hanging request returns a visible error instead of leaving the button disabled forever. Signed-in users without a completed owned-property/room-type setup run automatic property matching and room discovery from the sign-in/sign-up flow. The map opens at `/map` after setup and calls FastAPI directly with `Authorization: Bearer <Supabase JWT>`. The browser never receives `INTERNAL_API_KEY`.

Runtime note: `frontend/src/main.ts` imports `zone.js` before bootstrapping Angular. Without this import the development server can return HTML successfully while the browser shows a blank white page because Angular fails during runtime startup. `frontend/src/styles.css` imports `mapbox-gl/dist/mapbox-gl.css`; without the official Mapbox CSS, marker DOM elements can exist in the page but not be positioned visibly on the map.

Auth UX note: the password visibility control uses a normal click handler plus a `mousedown` focus guard. This lets users reveal/hide the password while typing without submitting the form or losing the active input unexpectedly.

**Dry run equivalent for this API slice:**
```bash
pytest api/tests -v
```

The market/agent endpoints are read-oriented, while scrape/onboarding mutation endpoints write durable `roomrate_scrape_jobs` rows for the Python worker.

**Production database migration preview:**
```bash

alembic upgrade head --sql
```

**Production database migration apply:**
```bash
# Apply only after DATABASE_URL points to the intended DB and a backup exists.
alembic upgrade head
```

**Backfill normalized tables from legacy room_rates:**

### 6. Code Walkthrough — File by File

#### `api/main.py`
**Purpose:** Creates the FastAPI app, configures CORS, includes routers and exposes `/health` plus `/ready`.

**Main object: `app`**
- **What it does:** Registers market, competitor, map, agent and WebSocket routes.
- **Why it works this way:** The frontend will call one stable API surface while the scraper and DB can evolve behind it.
- **Edge cases handled:**
  - Startup/shutdown logging
  - Explicit CORS origins from env
  - Separate tags in Swagger UI
  - DB-free liveness and PostgreSQL-backed readiness
  - Scheduler starts only in local `all` mode, never in the production API process

**Key logic explained:**
```python
app.include_router(market.router, prefix="/api/v1/market", tags=["Market"])
app.include_router(competitors.router, prefix="/api/v1/competitors", tags=["Competitors"])
app.include_router(maps.router, prefix="/api/v1/maps", tags=["Maps"])
app.include_router(agents.router, prefix="/api/v1/agents", tags=["Agents"])
app.include_router(onboarding.router, prefix="/api/v1/onboarding", tags=["Onboarding"])
app.include_router(scrape_jobs.router, prefix="/api/v1/scrape-jobs", tags=["Scrape Jobs"])
app.include_router(tracking.router, prefix="/api/v1/tracked", tags=["Tracked Competitors"])
app.include_router(notifications.router, tags=["Notifications"])
```

#### `api/config.py`
**Purpose:** Loads runtime settings from `.env`.

**Main function: `get_settings()`**
- **What it does:** Returns a cached `Settings` instance.
- **Why it works this way:** Avoids hardcoded credentials and keeps config centralized.
- **Edge cases handled:**
  - Empty `DATABASE_URL` is allowed at import time so tests can override dependencies.
- CORS origins are split from comma-separated env text.
- Production refuses `ROOMRATE_PROCESS_ROLE=all`, invalid retry ranges, or a worker with the scheduler disabled.

#### `api/db.py`
**Purpose:** Lazily creates the SQLAlchemy engine and yields DB connections.

**Main function: `get_engine()`**
- **What it does:** Creates a SQLAlchemy engine only when the first DB query is executed.
- **Why it works this way:** Tests and import-time app loading do not need a live database.
- **Edge cases handled:**
  - Missing `DATABASE_URL` raises a clear `RuntimeError`
  - Missing SQLAlchemy raises a dependency-specific `RuntimeError`

#### `api/repositories/room_rates_repository.py`
**Purpose:** Contains SQL for reading room-rate rows from either the legacy table or the normalized compatibility view.

**Main function: `fetch_room_rates(filters)`**
- **What it does:** Reads rows using optional destination/check-in/check-out, occupancy, normalized room type, scrape job, tracked competitor and amenities filters.
- **Why it works this way:** The service layer stays focused on business aggregation, not SQL. The relation is selected from hardcoded safe values using `ROOMRATE_RATE_SOURCE`.
- **Edge cases handled:**
  - Optional destination/date/occupancy filters
  - Optional repeated amenities matched against stored `facilities`
  - Optional `scrape_job_id` for reading the exact live scrape result set that just completed
  - Optional selected-competitor scope for saved checkbox sets
  - Bounded result limit
  - SQLAlchemy text parameters instead of string concatenation
  - Tracked competitor filters explicitly bind the saved competitor row to the outer `rates.property_id`. The category side follows the request: with a `room_type_category` the predicate is `tc.room_type_category IN (<comparable pool>)`, because tracked rows are keyed by the category the user searched under, not by the row's own; without one it falls back to `tc.room_type_category = rates.room_type_category`.
  - Amenity filters generate bound `ILIKE` parameters instead of relying on a PostgreSQL array cast, which keeps the query stable across SQLAlchemy/driver parameter binding. Popular facility labels such as `Free WiFi`, `Swimming pool` and `Sea view` expand to English/Greek aliases before SQL execution.
  - Destination filters expand known aliases before SQL execution, so user input like `Faliraki` can match Booking rows stored as `Φαληράκι`.

**Comparable room categories:** `room_type_category` is expanded through `comparable_room_type_categories` (`api/services/room_rates_normalizer.py`) before it reaches SQL, so `room_type_category=double` on `/api/v1/market/*`, `/api/v1/maps/competitors` and `/api/v1/competitors` also returns `twin` rows, and vice versa. Greek Booking labels sell one room as «Δίκλινο Δωμάτιο με 1 Διπλό ή 2 Μονά Κρεβάτια», which normalizes to `twin`, while a plain «Δίκλινο» room normalizes to `double`, so equality discarded exactly the competitors a hotelier competes with. Round 4.5 extends the same read-time pool to price history, alert evaluation, tracked-competitor preselection and completed-job restore. Stored category keys and alert payload vocabulary remain exact; no data is relabelled. Pooled tracking reads collapse duplicate property ids to the newest active row, so a competitor saved once under `double` and once under `twin` cannot inflate the onboarding checklist. Exact-category match scoring still ranks the requested bucket first.

**Source modes:**
```text
ROOMRATE_RATE_SOURCE=normalized  -> SELECT ... FROM roomrate_latest_room_rates
ROOMRATE_RATE_SOURCE=legacy      -> SELECT ... FROM room_rates
```

Normalized is now the default read source after smoke testing all dashboard and agent endpoints. If normalized reads show an issue, set `ROOMRATE_RATE_SOURCE=legacy` and restart the API. The normalized view now returns the latest completed scrape run per account, canonical destination, date range, adults, children and rooms, so dashboards do not mix stale historical runs with the current market snapshot.

For normalized reads, every query is scoped by account. Browser requests now use `Authorization: Bearer <Supabase JWT>`, and FastAPI maps that verified auth subject to `roomrate_user_identities`, `roomrate_accounts`, and `roomrate_memberships`. `X-API-Key` and `X-RoomRate-Account-ID` remain only as internal/local fallback paths.

#### `api/services/destination_aliases.py`
**Purpose:** Keeps a small deterministic alias map for destinations whose Booking city labels can be returned in English or Greek.

**Main functions:**
- `normalize_destination_key(value)`: creates an accent-insensitive, case-insensitive lookup key.
- `destination_variants(destination)`: returns all known variants for a destination before the repository builds the SQL filter.
- `canonical_destination(destination)`: returns the stable grouping key, e.g. `Faliraki`, `faliraki` and `Φαληράκι` all become `faliraki`.

**Why it works this way:** The live scrape can search with an English destination, while Booking may persist the returned city in Greek. The API keeps both values: `raw_destination` preserves what the user typed, while `canonical_destination` groups jobs/runs/views consistently.

#### `api/dependencies.py`
**Purpose:** Handles internal API-key validation and current account resolution.

**Main functions:**
- `verify_api_key(api_key)`: validates `X-API-Key`.
- `build_account_context(api_key, account_id_header, auth_subject)`: parses the tenant account UUID.
- `get_market_service(account)`: creates `RoomRatesRepository` with the resolved `account_id`.
- `get_scrape_job_service()`: creates `ScrapeJobService` with the PostgreSQL job repository and Booking scraper runner.

**Why it works this way:** `X-API-Key` is still the service-level guard, while `X-RoomRate-Account-ID` gives every dashboard/API request a tenant scope. Later, the same `AccountContext` can be built from a verified user JWT instead of a trusted header.

**Errors handled:**
- Invalid API key -> `403 Invalid API key`.
- Invalid `X-RoomRate-Account-ID` -> `422 X-RoomRate-Account-ID must be a valid UUID`.

#### `api/schemas/scrape_jobs.py`
**Purpose:** Defines request/response models for scrape-job creation and status polling.

**Main models:**
- `ScrapeJobCreate`: destination, raw/canonical destination, check-in/check-out, optional owned property, adults, children and rooms.
- `ScrapeJobResponse`: persisted job id, tenant account id, job status timestamps, retry counters, next retry time, error message, linked scrape-run count and nullable versioned `result_summary`.

**Validation rules:**
- `check_out` must be after `check_in`.
- `destination` cannot be blank.
- `raw_destination` defaults to the submitted `destination`; `canonical_destination` is derived server-side.
- `adults >= 1`, `children >= 0`, `rooms >= 1`.

#### `api/repositories/scrape_jobs_repository.py`
**Purpose:** Persists and reads `roomrate_scrape_jobs`.

**Main functions:**
- `create_job(account_id, request)`: inserts a `queued` job scoped to the current account.
- `get_job(account_id, job_id)`: fetches one account-scoped job and counts linked scrape runs.
- `list_jobs(account_id, limit)`: returns recent jobs for polling/history UI.
- `claim_job`, `heartbeat`, `complete_job`, `mark_failed`: lifecycle updates used by the worker. Completion stores `result_summary` in the same fenced transaction as the terminal status.
- `retry_or_fail`: atomically returns a failed attempt to `queued` with `next_attempt_at`, or makes it terminal after `max_attempts`.
- `fail_stale_jobs`: requeues a job whose worker heartbeat disappeared; only exhausted jobs become terminal.

All transitions are fenced on the expected current status, so a dead or late worker cannot overwrite the state chosen by another worker or the sweeper.

**Why it works this way:** The API never trusts a browser-provided account id directly. Every job write is scoped through `AccountContext`, and optional `owned_property_id` must belong to the same account.

#### `api/services/scrape_job_service.py`
**Purpose:** Orchestrates job lifecycle and bridges queued API jobs to the existing Booking scraper.

**Main classes:**
- `ScrapeJobService`: creates jobs, lists jobs and runs background job execution.
- `BookingScrapeJobRunner`: converts a persisted job into `python -m scraper` CLI args.
- `ScrapeJobCommand`: runtime command containing account, job id, destination, raw/canonical destination, dates and occupancy.

**Worker behavior:**
1. FastAPI creates `roomrate_scrape_jobs.status = queued` and returns `202`.
2. The standalone Python worker selects only ready jobs (`next_attempt_at <= now()`).
3. An atomic claim marks the job `running`, increments `attempt_count` and records worker identity plus heartbeat.
4. Runner starts the existing Booking scraper with `--account-id`, `--scrape-job-id`, `--scout-cache-hours 0`, bounded UI-driven limits from `filters_payload`, and the selected normalized room category. The Angular MVP deliberately keeps this first live search broad and does not push transient sidebar amenities into the scraper payload, because Booking facility labels are inconsistent and can easily remove every competitor.
5. Normalized writer saves packages and links `roomrate_scrape_runs.scrape_job_id`.
6. The scraper emits exactly one `ROOMRATE_RESULT_SUMMARY {json}` stdout sentinel on every successful exit. The runner forces UTF-8 on both subprocess ends (`PYTHONUTF8=1`, `encoding="utf-8"`) because Windows ANSI decoding can otherwise lose Greek logs and the final sentinel. It accepts only the last version-1 object; a missing or malformed payload becomes `NULL` and is logged without turning a successful scrape into a failed job.
7. Service stores the summary and marks the job `completed` atomically. Operational failures return to `queued` with capped exponential backoff and full jitter; the final allowed attempt becomes `failed` and stores no summary.

In local `ROOMRATE_PROCESS_ROLE=all`, FastAPI also issues a best-effort
`BackgroundTasks` kick for faster feedback. PostgreSQL remains the source of
truth, so a restart cannot lose the job.

#### `api/worker.py`
**Purpose:** Runs APScheduler as a standalone Python process, separate from FastAPI web workers.

- Starts the schedule tick, queued-job executor, stale-heartbeat recovery and cleanup jobs.
- Handles `SIGINT`/`SIGTERM` and shuts down without accepting new scheduler callbacks.
- Refuses to start under the production `api` role or with the scheduler disabled.

#### `api/services/retry_policy.py`
**Purpose:** Calculates capped exponential backoff with full jitter.

```python
retry_window = min(max_seconds, base_seconds * (2 ** (attempt - 1)))
return randomizer(0.0, float(retry_window))
```

The random delay prevents many failed jobs from retrying the provider at the
same instant. The cap prevents an old job from remaining deferred indefinitely.

#### `migrations/versions/20260722_0016_durable_scrape_job_retries.py`
**Purpose:** Adds durable retry state and the ready-queue index.

- Adds `attempt_count`, `max_attempts` and `next_attempt_at`.
- Enforces `attempt_count >= 0` and `max_attempts BETWEEN 1 AND 10`.
- Adds `ix_roomrate_scrape_jobs_queued_ready` for worker polling.
- Repairs the property/observation history index name on older renamed schemas.

#### `migrations/versions/20260828_0023_add_scrape_job_result_summary.py`
**Purpose:** Carries truthful filter outcomes from the scraper to the API and map UI.

- Adds nullable JSONB `roomrate_scrape_jobs.result_summary`.
- Existing completed jobs remain `NULL` and therefore use the generic empty-state text.
- New successful jobs store version, `rows_seen`, per-stage `{before, after}` counts and `rows_written`.
- Deploy with `alembic upgrade head` before starting the updated API/worker code.

Frontend-created jobs pass `--scout-cache-hours 2` (scheduled jobs `12`). The scout cache holds only the area's hotel list (names, links, coordinates), never prices: every job deep-crawls live prices, so reusing a list up to 2 hours old for the same stay and party only skips a paid scout run. The database still stores completed scrape results for audit/history and API reads, but the map does not use stale stored markers as the source of a new search.

#### `api/models/market.py`
**Purpose:** Defines the production normalized PostgreSQL schema with SQLAlchemy models.

**Main tables:**
- `roomrate_accounts`: tenant account for one hotel operator/company.
- `roomrate_user_identities`: external auth user identity from Supabase Auth.
- `roomrate_memberships`: user-to-account role mapping.
- `roomrate_owned_properties`: properties owned or managed by an account, optionally linked to the matching global Booking property. Stores `raw_destination` and `canonical_destination` from onboarding.
- `roomrate_scrape_jobs`: account-scoped scrape requests from the future frontend.
- `roomrate_scrape_runs`: one row per executed Booking/Apify market scrape request, optionally linked back to the requested scrape job and carrying raw/canonical destination plus adults/children/rooms.
- `roomrate_properties`: canonical competitor property dimension.
- `roomrate_rate_observations`: one property-level market state inside a scrape run.
- `roomrate_room_packages`: package/room-level offers under an observation.
- `roomrate_amenities`: normalized amenity dimension.
- `roomrate_property_amenities`: property-to-amenity bridge table.
- `roomrate_raw_ingestion_events`: immutable raw payload storage for debugging and replay.

**Why it works this way:** The old `room_rates` table is scraper-shaped. The new schema separates raw ingestion, canonical properties, scrape runs, package offers and analytics views. This gives production-safe history, idempotent loading, constraints, indexes and cleaner API evolution.

**Production rules enforced:**
- UUID primary keys.
- Foreign keys between scrape runs, properties, observations and packages.
- Unique constraints for idempotent scraping/backfill.
- `NUMERIC(10,2)` for prices.
- `NUMERIC(9,6)` for coordinates.
- Check constraints for dates, coordinates, prices, reviews and rooms left.

#### `migrations/versions/20260517_0004_rename_roomrate_schema_prefix.py`
**Purpose:** Renames the production schema prefix to the RoomRate brand.

**What changed:**
- Logical SQLAlchemy tables and API read views now use `roomrate_*`.
- The migration safely renames existing deployed objects from the previous prefix to `roomrate_*`.
- Fresh databases created from the edited migration history already create the `roomrate_*` schema.

#### `migrations/versions/20260521_0006_add_destination_canonicalization.py`

**Key logic explained:**
```python
record_id = _make_record_id(hotel_url or hotel_name, room_name, str(package_id), config)
facilities = _normalize_facilities(raw_fac)
normalized_rates.append(normalize_room_rate_row(row, provider=config.provider))
```

`record_id` includes stable property identity (provider URL when available), room, package id, stay dates, guests, children and rooms. This prevents different listings with the same display/fallback name, and future scrape runs for different dates, from being silently skipped as duplicates.

Room-name filtering groups by normalized `hotel_url`; only when URL is absent does it use the normalized display name. Unknown/fallback names without URL are treated as independent rows because merging them would invent a property identity. Within each property, every offer from the strongest available tier survives in original order, including duplicate package variants and duplicate DataFrame indices.


The scraper writes normalized production tables only. The legacy `room_rates`
write path (`--write-legacy` / `--no-legacy`) was removed in the backend

`False`, so the branch had been dead in every production scrape. The existing
`room_rates` table and its read path (`ROOMRATE_RATE_SOURCE=legacy`) are
untouched, but they now only ever serve **historical** rows.

**Runtime optimizations:**
- Frontend-created live jobs pass `--scout-cache-hours 0`, so the first stage always calls Booking/Apify fresh and skips scout-cache writes.
- Signup property discovery first tries `property name + location`. If Booking returns zero items, it retries with location-only search and then ranks candidates by name similarity. This is required because the Apify Booking actor can return zero results for property-specific search strings even when the property exists in the destination results.
- Deep-crawl URLs are normalized and deduplicated before batching.
- Scout requests and cache keys include `adults`, `children`, `rooms`, `currency` and `language`; results from a different availability query cannot be reused accidentally.
- Scout cache writes use a natural-key unique constraint plus PostgreSQL upsert, so concurrent scheduled jobs cannot create duplicate candidate rows.
- Apify retries use capped exponential backoff with full jitter, reducing synchronized retry spikes during provider throttling.
- A failed deep-crawl batch fails the whole snapshot by default. `--allow-partial-batches` is an explicit diagnostic escape hatch when incomplete market coverage is acceptable.
- Batch and row-normalization failures append anonymous records to `logs/error_log.csv`; `--dry-run` remains write-free.
- `deep_crawl_max_items` is split across batches instead of being applied in full to every batch, which prevents accidental multiplication of Apify items.
- `filters_payload.limit` is bounded by the FastAPI runner before it becomes `--scout-max-items`.
- `--required-amenity` still exists for CLI/API advanced use, but the Angular MVP does not send it during `Find Competitors`.
- `--room-type-category` is always passed from the selected owned-room catalog item and is the primary matching rule for `Find Competitors`. The Angular map now also sends the selected owned-room catalog label as `room_type`, so the scraper can match competitor catalog rows by similar room names after the normalized category filter. Meal and cancellation filters remain supported by the scraper for future advanced controls, but the Angular MVP does not auto-apply them because they are too strict and can remove valid competitors. Price is intentionally not used for matching.

In `--dry-run` mode the script still calls Apify so the live payload shape can be validated, but it does not create a database engine, does not write CSV, and does not update `scout_cache`.

**Business formulas used:**

Market Average Price (Μέση Τιμή Αγοράς):
```text
Average Price = sum(price_per_night_eur) / number_of_room_packages
Code: price_avg_eur = round(mean(prices), 2)
```

Market Median Price (Διάμεση Τιμή Αγοράς):
```text
Median Price = middle value of sorted nightly prices
Code: price_median_eur = round(median(prices), 2)
```

Lowest Competitor Price (Χαμηλότερη Τιμή Ανταγωνιστή):
```text
Price Min = min(price_per_night_eur) per hotel or market
Code: price_min_eur = round(min(prices), 2)
```

Rooms Left Demand Signal (Ένδειξη Ζήτησης από Διαθέσιμα Δωμάτια):
```text
Competitor rooms_left = minimum rooms_left among that hotel's packages
Code: rooms_left=min(rooms_left_values) if rooms_left_values else 0
```

#### `api/routers/agents.py`
**Purpose:** Exposes Smart Advisor/Amenities context and an audited hybrid
price-recommendation endpoint.

`POST /api/v1/agents/price-recommendation` validates ownership, reuses an
account-scoped 15-minute cache for identical requests, enforces a configurable
daily account quota, applies the statistical/LLM validators and a maximum move
from the property's own reference price, then persists the complete decision
in `roomrate_price_recommendation_audits`. If audit persistence fails, the API
returns 503 instead of delivering an unaudited financial decision.

**Business formula used:**

Μέγιστη Επιτρεπτή Μεταβολή Τιμής (Maximum Allowed Price Change):

```text
Lower Bound = Own Reference Price × (1 − Max Change % / 100)
Upper Bound = Own Reference Price × (1 + Max Change % / 100)
Recommended = min(max(Raw Recommendation, Lower Bound), Upper Bound)
```

Exact Python:
```python
lower_bound = own_price * max(0.0, 1.0 - max_change_pct / 100.0)
upper_bound = own_price * (1.0 + max_change_pct / 100.0)
recommended = min(max(recommendation.recommended_price_eur, lower_bound), upper_bound)
```

Το όριο εφαρμόζεται και στο εύρος χαμηλής/υψηλής τιμής ώστε να ισχύει πάντα
`low <= recommended <= high`. Αν δεν υπάρχει θετική τιμή αναφοράς, η
προϋπάρχουσα market-band επικύρωση παραμένει το ενεργό guardrail.

**Purpose:** Implements step 1 of `/setup`: confirm the zero-cost auto-setup

**Key branching logic:**


The empty-id branch is critical: after auto-setup fails, `/me` correctly has no

therefore retries a failed save without launching another paid, minutes-long

without a discovery-job id; if reconciliation itself fails, the original API
error stays visible and the UI refuses a duplicate-risk POST. The exact
candidate and request body are snapshotted before POST, and candidate/refine
controls remain locked while saving or while the create outcome is ambiguous,
so later UI changes cannot corrupt reconciled metadata. A successful create invalidates
the shared `/me` cache before the next guarded navigation. The mount-time
fallback search preserves the stored auto-setup explanation, while an explicit
user search clears it.

#### `frontend/src/app/onboarding/setup-room-step.component.ts`
**Purpose:** Implements step 2 of `/setup`: waits for the owned-property room
discovery job, lets the user choose the baseline room category, and persists it
before step 3.

The component polls only `queued`/`running` jobs and handles completed, failed,
unexpected-status and five-minute timeout outcomes explicitly. The budget is a
true monotonic deadline, not a poll-attempt count: `poll-deadline.ts` races each
job HTTP read against its remaining `performance.now()` budget and bounds every
delay to the same deadline. The underlying HTTP promise may finish later, but
its result is consumed without reaching UI state. Poll delays are cancellable:
destruction invalidates the active reload token, releases any pending timer
and request-race cancellation immediately, and every continuation re-checks
that token before writing a signal or emitting.

Reload and save are single-flight operations and cannot overlap. A failed
catalog load retries discovery/catalog loading; a failed selection retries the
same selection PUT instead of unnecessarily repeating discovery. Empty and
error states offer both retry and an explicit route to the map. The room-step
skip passes `allowIncompleteSetup` only in that Angular Router navigation's
`NavigationExtras.state`; a later ordinary SPA map link has no such state and
resumes incomplete setup at step 2. Provider/API details are never rendered
here: load failures and save
failures each map to their own stable Greek message. Sample price
uses a null/undefined check, so a valid observed `0 €` remains visible rather
than being mistaken for missing data.

#### `frontend/src/app/onboarding/poll-deadline.ts`
**Purpose:** Provides the pure monotonic remaining-time calculation and the
deadline race used by room discovery polling.

The helper accepts an operation factory and checks remaining time before
invoking it, so work never starts when the deadline has already expired. It
converts resolve, synchronous throw, rejection, cancellation and deadline into
explicit outcomes. Once an operation starts, its deadline branch does not fake
API-client cancellation; resolve/reject handlers consume a late settlement so
it cannot become an unhandled rejection.

#### `frontend/src/app/onboarding/setup-search-step.component.ts`
**Purpose:** Implements step 3 of `/setup`: the explicit cost gate and the first
paid competitor search.

Before the paid button exists, the component invalidates the navigation cache,
loads authoritative `/me`, requires the same owned-property id plus a selected
room category, destination and raw destination, then builds one frozen request
with the stay dates, occupancy and filter payload. The summary renders only
from that request, so stale workflow-storage values can never disagree with the
POST. A `/me` failure or property mismatch shows stable Greek preparation
guidance; its retry only reloads the intent and still requires a separate paid
click. Initialization, preparation retry and «Αργότερα» perform no scrape-job
POST. Double clicks on the enabled start action remain single-flight.

Immediately before POST, `recentScrapeJobs()` records the existing job ids. If
the POST response is lost, retry first lists the account's durable jobs and uses
`search-job-reconciliation.ts` to require both a new id and an exact match of
every request field. A match resumes that committed job. An authoritative
no-match safely repeats the same immutable request; if the list itself fails,
the UI blocks a duplicate-risk POST and shows a stable Greek explanation.

`ApiClientError` preserves the existing user-facing client messages while
adding `kind` (`transport`, `timeout`, `http`) and HTTP `status`. Only transport,
timeout and 5xx POST failures enter reconciliation. A deterministic 422 clears
the invalid intent and requires preparation plus another explicit start. A 429
from an ordinary POST keeps the exact intent and offers a later direct retry
without a recent-job read. If the repeated POST after an authoritative
reconciliation no-match returns 429, the component preserves that explicit
reconciliation context: the next action lists first and adopts an exact
late-visible original job before considering another POST. Raw
FastAPI/provider details are never rendered.

`scrape-job-poller.ts` polls only queued/running jobs inside one real monotonic
five-minute deadline. It races held HTTP reads and poll delays against component
destruction, so a late completion cannot update state or emit navigation after
the step is gone. Provider/API details are never rendered.

**Key cost-gate logic:**
```typescript
const recent = await this.onboarding.recentScrapeJobs(50);
this.baselineJobIds.set(new Set(recent.map((job) => job.id)));
return this.postIntended(intended, token);
```

The pre-POST list is read-only. It makes later reconciliation authoritative
without introducing a backend idempotency contract.

#### POST /api/v1/agents/price-recommendation
**Purpose:** Hybrid (statistical + optional LLM) nightly-price recommendation
for the account's owned room.

Every LLM answer passes a deterministic post-validator before it can reach a
user: prices must be positive, `low <= recommended <= high` must hold, and the
recommended price must sit inside a market plausibility band
(`[0.5 × P25, 1.5 × P75]`). A failing answer is silently replaced by the
statistical baseline. `confidence` is never the model's self-assessment — it
is computed from data quality alone (`high`: ≥5 runs + market distribution +
7-day trend, `medium`: ≥2 runs + market distribution, `low`: anything
thinner), so identical history always yields identical confidence.

**Request body:**
```json
{
  "owned_property_id": "00000000-0000-0000-0000-000000000456",
  "room_type_category": "double",
  "check_in": "2099-07-15",
  "check_out": "2099-07-18",
  "adults": 2,
  "children": 0,
  "rooms": 1
}
```

**Response:**
```json
{
  "statistics": { "sample_runs": 2, "market_median_eur": 110.0, "notes": [] },
  "recommendation": {
    "recommended_price_eur": 112.0,
    "price_range_low_eur": 98.0,
    "price_range_high_eur": 124.0,
    "confidence": "medium",
    "reasoning": "...",
    "key_factors": ["Market median EUR 110.0"],
    "source": "agent"
  },
  "recommendation_available": true,
  "audit_id": "00000000-0000-0000-0000-000000000999",
  "generated_at": "2026-07-26T10:15:00Z",
  "cached": false,
  "model_version": "claude-opus-5-5",
  "prompt_version": "2026-07-26.v1"
}
```

**Insufficient data:** the recommendation is anchored on MARKET knowledge —
the trend-adjusted statistical baseline or the market median. The owner's own
reference price is deliberately not an anchor: echoing the input back
("we recommend the price you already charge") reads as an analysis the data
cannot support, since with no scraped history every market statistic renders
empty beside a confident headline number. When no market anchor exists the
endpoint returns `recommendation_available: false` with
`recommendation: null` (never a fabricated €0 and never the owner's own
price); `statistics.notes` explains what is missing.

**Audit trail is best-effort:** the cache lookup, the daily-quota count and
the audit insert each degrade to a logged warning rather than failing the
request. A database missing migration 0020 would otherwise 500 every call,
and a transient insert failure would discard an already-billed LLM answer —
so on insert failure the full audit record is emitted to the application log
and the caller still receives its recommendation (without an `audit_id`).

**Errors:**
```text
404 Owned property, canonical destination, or room category not found
422 Invalid or past stay dates / occupancy
429 Daily account recommendation quota reached
503 Recommendation audit could not be persisted
```

```json
  "ticket": "opaque-url-safe-token",
  "expires_in_seconds": 60
}
```

#### WebSocket /ws/alerts
**Purpose:** Realtime account-scoped notification stream (price alerts).

**Authentication:** `?ticket=<one-time ticket>` from `POST
/api/v1/notifications/ws-ticket`. Browser JWTs are deliberately NOT accepted
in the URL (query strings leak into server/proxy logs and browser history);
a legacy `?token=` handshake closes with 4401. The internal fallback
`?api_key=<INTERNAL_API_KEY>&account_id=<uuid>` remains for
server-side/staging tooling and REQUIRES an explicit account id.

**Initial message:**
```json
{
  "type": "connected",
  "message": "RoomRate alerts connected"
}
```

**Alert frames:** `{"account_id": ..., "notification": {"id", "notification_type",
"title", "message", "payload", "is_read", "created_at"}}` — oversize payloads
collapse to `{"id"}` and the client refetches over REST.

### 10. Error Handling Reference

| Error | Location | Cause | What happens |
|-------|----------|-------|--------------|
| RuntimeError | api/db.py | Missing DATABASE_URL | DB endpoint fails with clear message |
| RuntimeError | api/db.py / repository | SQLAlchemy missing | Developer is told to install requirements |
| HTTPException 401 | api/dependencies.py | Missing/invalid Supabase bearer token or missing internal API key | Request rejected |
| HTTPException 403 | api/dependencies.py | Wrong internal X-API-Key | Request rejected |
| HTTPException 422 | api/dependencies.py | Invalid X-RoomRate-Account-ID | Request rejected before DB read |
| HTTPException 422 | api/routers/_filters.py | Invalid date range or limit | Request rejected with detail |
| HTTPException 422 | api/routers/scrape_jobs.py | Invalid scrape-job dates, occupancy, or owned property scope | Job is not created |
| HTTPException 429 | api/routers/agents.py | Daily recommendation quota exhausted | No new analysis runs; an identical unexpired cache entry can still be reused |
| HTTPException 503 | api/routers/agents.py | Audit persistence failed | The recommendation is withheld so no unaudited financial decision reaches the UI |
| HTTPException 404 | api/routers/notifications.py | Alert rule is missing, belongs to another account, or references an inaccessible property | Mutation is rejected without revealing another tenant's data |
| Retryable scrape failure | api/services/scrape_job_service.py | Timeout, provider failure, subprocess error or transient OS error | Job returns to `queued` with `next_attempt_at`; after `max_attempts` it becomes `failed` |
| Lost worker heartbeat | api/repositories/scrape_jobs_repository.py | Worker/process died while job was `running` | Sweeper requeues it with backoff, or fails it if attempts are exhausted |
| HTTP 503 | api/main.py `/ready` | PostgreSQL unavailable or local scheduler stopped | Deployment removes the FastAPI instance from traffic without restarting a live process blindly |
| Partial deep crawl | scraper/deep_crawl.py | One or more parallel actor batches exhaust retries | Entire snapshot fails by default; details are appended to `logs/error_log.csv` |
| Auth/API timeout | frontend/src/app/services/auth.service.ts / frontend/src/app/pages/auth-page.component.ts / frontend/src/app/services/api-client.service.ts | Supabase, FastAPI, or Booking lookup takes too long | UI unlocks and shows the exact failing step instead of staying on `Signing in`; scrape-job polling allows several minutes for live Apify runs |
| Property apply failure | frontend/src/app/onboarding/setup-property-step.component.ts | Create/replace request fails after the user has selected a candidate | The original backend/API error remains visible; a first-property create is reconciled through fresh `/me` before another POST, while a replace retry does not rerun candidate discovery |
| Room discovery/load/save failure | frontend/src/app/onboarding/setup-room-step.component.ts | Job failure/unexpected status, network/catalog error, five-minute deadline, or selected-room PUT failure | UI stays on step 2, shows a stable Greek load/save/timeout message with retry and skip guidance, and never exposes provider details |
| First-search start/reconciliation failure | frontend/src/app/onboarding/setup-search-step.component.ts | Paid-job POST response is lost, recent-job reconciliation fails, polling fails, or the real five-minute deadline expires | UI stays on step 3 with a stable Greek message; retry resumes the matching durable job or repeats the immutable request only after an authoritative no-match, never after an unavailable reconciliation |
| First-search authoritative preparation failure | frontend/src/app/onboarding/setup-search-step.component.ts | `/me` fails, property id differs, or selected category/destination fields are absent | Paid action and summary stay hidden; retry only reloads authoritative intent and performs no POST |
| First-search HTTP 422 / 429 | frontend/src/app/onboarding/setup-search-step.component.ts | Request validation is deterministic, or the account quota is exhausted | 422 discards the invalid intent and requires preparation; an ordinary 429 retains it for a later direct retry, while a 429 after an ambiguous POST and authoritative no-match preserves reconciliation context so the next action lists before posting |
| Empty DB result | api/services/market_service.py | No matching rows | API returns zero metrics or empty list |
| WebSocketDisconnect | api/routers/notifications.py | Browser disconnects | Connection removed from manager |

Layout note: the map uses a screenshot-style market layout: the filter sidebar is collapsed by default, the Mapbox canvas takes the left side, and the market snapshot plus competitor cards stay in the right sidebar. The first required filter is still the user's discovered room catalog from `roomrate_owned_property_room_types`; opening `Filters` reveals that workflow without shrinking the default map view. `Find Competitors` creates a manual `competitor_search` job, forces a fresh Booking scout instead of using `scout_cache`, passes the selected normalized room category and selected room catalog label into the scraper, polls `GET /api/v1/scrape-jobs/{job_id}` directly through FastAPI for up to several minutes, then refreshes marker candidates through `/api/v1/maps/competitors?scrape_job_id=...` so the cards come from the exact completed live job. The immediate post-scrape refresh intentionally avoids amenity parameters so stale or overly strict facility selections do not hide all cards. Facility filters are displayed as general `Most popular facilities` labels and matched through aliases rather than raw room-feature strings like `15 m2`. When the user opens the map, Angular clears the in-memory competitor state (`resetCompetitorSearchState`) but deliberately KEEPS `lastCompetitorJobId` and the stored checkbox selection in local storage, because `restoreLatestCompetitorSearch` runs right after it and reloads the last completed search — its cards, markers and saved selection — instead of forcing a fresh Apify-costing scrape on every navigation back to the map; a stored job that no longer restores is cleaned up there. The component also clears any leftover marker DOM before Mapbox initialization and again after Mapbox load, so local dev/HMR sessions cannot keep old marker dots when Angular has zero current competitors. `Add selected to tracked` still appends the selected competitors to the longer-term tracked competitors in PostgreSQL without removing older tracked rows. If the scrape only finds the user's own property and it is excluded, the right sidebar shows a clear no-results explanation. Every result of a completed search is plotted on the map automatically, both after a live search and on restore, so the hotelier never has to discover the map through a checkbox. Checkbox selections choose which rooms are TRACKED, and the right sidebar's «Μόνο τα επιλεγμένα στον χάρτη» toggle optionally narrows the map to just those selected rooms. Starting a new search clears old cards and markers before polling so stale marker dots do not remain on the map while the new right-side cards are loading. The cleanup also removes any leftover `.roomrate-marker-dot` DOM nodes inside the Mapbox container, which protects local dev/HMR sessions from showing markers that no longer exist in Angular state. Competitors render as compact colored dot markers: teal for lower prices, brown for mid-range prices and red for high prices; rooms selected for tracking carry `data-selected="true"` plus an extra halo ring so they stay distinguishable in every price class. Rows whose cheapest offer has no coordinates stay in the card list but cannot be drawn, and the map overlay states which reason left it empty — no search yet, nothing drawable, or the selected-only filter hiding everything. Marker CSS deliberately avoids `transform` transitions because Mapbox uses transforms internally to position markers during pan and zoom, and popup z-index is kept above marker z-index so marker dots cannot appear on top of popup cards.

Marker popups use a separate room-type section instead of a compressed label/value row. This keeps long Greek Booking room names readable and avoids text collisions such as the old `RoomΚρεβάτια` rendering.

Round 4.5 empty-result behavior is job-derived, not inferred through extra API probes. The map receives `result_summary` with the completed job and distinguishes: rows eliminated by the comparable room-category stage, rows that reached that stage but were eliminated by later name/meal/cancellation/amenity filters, and a generic zero-result case. Historical jobs created before migration 0023 have `NULL` summaries and intentionally use the generic message. A completed `double` job can restore while `twin` is selected (and vice versa); job-scoped reads use the job's exact stored category and stay dates, while the user's currently selected owned-room value remains unchanged.

Scrape efficiency note: the Angular `Find Competitors` flow defaults to a smaller result limit and sends an explicit bounded `deep_crawl_max_items` value, so live searches do not ask Apify for a much larger room-package crawl than the UI needs. The automatic owned-property discovery job also uses direct URL mode with `limit=1` and `deep_crawl_max_items=30`, because it only needs enough rows to discover the user's own room catalog.

Tracked-set note: `Add selected to tracked` is enabled only after the user selects at least one competitor card, and the success/error feedback is displayed in the right results sidebar next to the button. Success feedback auto-hides after a few seconds. The Angular map uses `POST /api/v1/tracked/competitors` so new selected rooms are added on top of previous tracked competitors. The older `PUT /api/v1/tracked/competitors` replace behavior remains available for a future management screen.

### 13. Known Limitations & Future Improvements

**Current limitations:**
- The PostgreSQL queue is durable and restart-safe, but there is no separate worker HTTP health endpoint; the hosting platform must monitor the `python -m api.worker` process and alerts should monitor queue age.
- The scraper is now modular, but provider payload contracts remain external and can change without notice; staging smoke tests against Apify are still required before each production release.
- Completed scrape rows are persisted in PostgreSQL because the API/agents need structured results, history and debugging. An explicit `Find Competitors` still forces a fresh scrape job, while simply opening the map restores the last completed search from `lastCompetitorJobId` rather than re-running (or re-paying for) it.
- Room-category and amenities matching still happens after Apify returns room/package rows; the Booking actor does not receive a true semantic room-type filter.
- Email/SMS delivery is intentionally not enabled: notifications are currently in-app and realtime. Add Resend/SendGrid or Twilio only when the business requires an external channel and consent rules are defined.
- The Angular map component remains large; its async state, date validation and Mapbox error lifecycle are hardened, but extracting filter/results subcomponents is still a maintainability improvement.
- Competitor room mapping uses exact/partial room labels plus normalized categories, not a full semantic ML matcher yet.
- Property grouping prefers the provider URL, but a provider URL change can still make the same physical hotel appear as a new identity; rows with neither URL nor trustworthy name stay intentionally unmerged.
- Completed jobs created before migration 0023 have no `result_summary`; they restore normally when they have scrape runs, but their empty state cannot explain which filter removed the rows.
- Popular-facility filtering currently matches stored `facilities` text through deterministic aliases; a dedicated package-level amenity matcher can be added later.
- `apify-shared==1.4.1` is pinned because `apify-client==1.9.4` is not compatible with the newer installed `apify-shared==2.2.0` package.
- Headless Edge rendered the colored marker dots and side panel, but Mapbox base tiles may depend on token/domain/network access in the actual browser session.

**Planned improvements:**
- Add KPI cards and competitor table around the completed Mapbox competitor map.
- Extend the current price-change rules with low `rooms_left` and market-average movement rule types.
- Add worker/queue operational metrics (oldest-ready-job age, retry rate, terminal-failure rate and provider latency).
- Multi-property account switcher and tracked competitor set management screen.
- Add an offline golden evaluation dataset and approval workflow before allowing pricing recommendations to trigger automatic rate publication.

### 14. Pre-production integration checks (require live infrastructure)

Phase F replaced the per-request Supabase token verification with **local JWT
verification** (signature + `exp` + `aud` via PyJWT; HS256 secret or RS256/ES256
JWKS, auto-detected from the token header). It is unit-tested with self-signed
tokens and a stubbed JWKS, but several behaviors can only be verified against
real infrastructure and are **deliberately not exercised in the unit suite**
(no PostgreSQL/Supabase is reachable in CI). Run these against a real
PostgreSQL + Supabase project before each production rollout.

**Runner:** `scripts/pre_production_checklist.py` automates the checks below
where possible — DB connectivity + `alembic` revision vs migration head,
read-only repository SQL smoke, normalized-schema duplicates/orphans/price-range
checks, critical hot-path index presence, the LISTEN/NOTIFY round-trip, the JWKS/JWT
config check, `/ready` database/process readiness (pass `--api-base-url` or set
`API_BASE_URL`), and scheduler config sanity. It prints a PASS/FAIL/SKIP
table (unconfigured pieces SKIP with a reason) and exits non-zero on any FAIL:

```bash
python scripts/pre_production_checklist.py --api-base-url https://api.example.com
```

The end-to-end scrape subprocess check and the key-rotation / real-token
verifications below remain manual:

- **JWKS against a real Supabase project.** Confirm `SUPABASE_JWKS_URL` (or the
  derived `<SUPABASE_URL>/auth/v1/.well-known/jwks.json`) serves the project's
  signing keys, that a real access token verifies, that the `kid`-cache refresh
  fires on key rotation, and that the `authenticated` audience matches. For
  HS256 projects, confirm a real token verifies with `SUPABASE_JWT_SECRET`.
- **Cross-process LISTEN/NOTIFY delivery.** Raise a notification on one API
  process and confirm a WebSocket client connected to a *different* process
  receives it (the `pg_notify` broadcaster + `NotificationListener` path).
- **Raw repository SQL.** Exercise the repositories' raw SQL against a real
  schema at migration head `20260727_0021`: scrape-job claim/heartbeat/retry/complete
  /fail transitions, ready-queue index and the partial unique active-market index, the advisory-
  locked schedule tick, the stale-job sweeper, `fetch_latest_vs_previous` and
  `fetch_price_series`, notification `event_key` dedup (`ON CONFLICT` on the
  partial unique index), one-time WS ticket mint/redeem, and `scout_cache`
  cleanup.
- **Process readiness.** Confirm `GET /ready` returns 200 for the API role and
  the hosting platform reports the separate `python -m api.worker` process as
  healthy. Stop a worker mid-job and verify the sweeper returns the job to
  `queued` with a future `next_attempt_at`.
- **Scrape subprocess.** Run an end-to-end job so the `python -m scraper`
  subprocess, its injected `PYTHONPATH`, timeout enforcement and heartbeating
  are exercised against the real scraper.

**Full-journey staging runner:** `scripts/staging_e2e.py` automates the whole
data journey against a live stack — scrape #1 → tracked competitors → price
history → a deterministic SQL price nudge (two live scrapes minutes apart see
identical prices, so run #1's stored prices are lowered to guarantee run #2
crosses the alert threshold) → scrape #2 with a live `/ws/alerts` WebSocket
attached via a one-time ticket → the `price_change` frame + REST feed row →
a validated `POST /api/v1/agents/price-recommendation`. It prints the same
PASS/FAIL/SKIP table and exits non-zero on any FAIL.

```bash
python scripts/staging_e2e.py --api-base-url http://127.0.0.1:8000
```

Requirements: an onboarded account, `INTERNAL_API_KEY` + `DATABASE_URL`, and
a process executing queued jobs (`ROOMRATE_PROCESS_ROLE=all` locally, or the
separate worker in staging). ⚠️ The two scrape steps spend real Apify credits
(run deliberately, not on a schedule).
